# Rust 多平台内容发布桌面软件：初始交接文档

- 整理日期：2026-11-10
- 文档用途：导入工作模式，作为创建项目和持续开发的依据。
- 项目暂名：Rust Social Publisher，正式名称后续再定。
- 当前阶段：已完成方向讨论与上游源码调研；尚未创建本项目仓库、编写应用、生成安装包或完成真实账号发布测试。
- 阅读约定：“已确定”来自本次讨论；“建议”是可直接用于开工的默认方案；“待验证”不代表已经实现或兼容。

## 1. 项目目标与已确定的方向

开发一个有完整桌面界面的多平台内容发布工具，统一管理账号、素材和发布任务。参考用户提供的自媒体管理软件截图中的功能组织，不依赖截图软件的品牌、源码或私有接口。

### 1.1 已确定

1. 应用界面和核心业务采用 Rust。
2. 原生桌面界面采用 GPUI / GPUI Kit 方向；不采用 Python 加网页前端，也不把浏览器页面作为主界面。
3. 移除 Python 运行时、Python worker 和 Python 后端服务。把 Python 程序冻结成可执行文件也不算完成这个目标。
4. social-auto-upload（下文简称 SAU）用于研究和移植平台发布流程，不作为运行时依赖。
5. 允许在发布执行层使用 Chrome / Chromium。主界面由 Rust 绘制，与后台用浏览器操作平台网站是两件事。
6. 以账号、素材、发布、任务结果这条主流程为首要目标，逐个平台实现真实可用的发布能力。

### 1.2 采用的技术方案

| 层次 | 方案 | 用途 |
| --- | --- | --- |
| 桌面界面 | Rust + GPUI Kit | 窗口、导航、账号列表、表单、任务表格、日志和设置 |
| 业务逻辑 | Rust | 校验、平台能力、任务调度、状态转换、恢复与取消 |
| 本地存储 | SQLite | 账号元信息、素材记录、草稿、发布任务与执行记录 |
| 异步执行 | Tokio 后台运行时 | 浏览器通信、上传等待、外部程序与任务事件 |
| 网页发布 | chromiumoxide + Chrome / Chromium | 通过 CDP 操作创作者平台页面 |
| B 站发布候选 | biliup 原生程序，必要时评估 Rust 核心库 | 复用现成的登录和投稿实现 |
| 上游参考 | social-auto-upload | 理解平台流程、字段、等待条件与异常处理 |

GPUI Kit 是 Longbridge 的 Rust 桌面组件与应用框架；原 gpui-component 仓库地址目前指向 gpui-kit，组件层仍存在。实际依赖名、导入路径和版本组合以开工时选定版本的官方示例为准，不混用不同时期的示例。[1][2]

这些是本项目的实现方向，不表示相关库已在用户目标电脑上完成验证。

## 2. 为什么可以完全去掉 Python

### 2.1 SAU 中 Python 原本承担的工作

以当前 SAU 的抖音模块为例，Python 通过 Patchright 驱动浏览器，完成登录状态管理、打开发布页、上传文件、填写内容、设置发布选项和检查结果等步骤。[4][5]

这部分价值主要在“已经研究过的平台操作流程”。Rust 可以承担相同职责，但需要移植和验证这些流程；删除 Python 解释器不会自动把原有脚本变成 Rust 程序。

迁移时重点核对：

- 登录完成和登录失效的判断。
- Cookie、浏览器 profile 和账号之间的对应关系。
- 文件上传、封面、标签、弹窗、iframe 等交互。
- 等待页面就绪、上传结束和平台处理结束的条件。
- 最终提交之后如何确认结果。
- 页面变化、超时、取消和网络中断的处理。

chromiumoxide 是 Rust 的异步 CDP 浏览器控制库，可启动或连接 Chrome / Chromium，并支持有界面和无界面模式。它不是 SAU 所用 Python 自动化接口的直接替代品，具体等待和交互行为需要重新实现。[3]

### 2.2 B 站存在更直接的复用路径

SAU 当前的 B 站运行层会查找或下载 biliup 原生可执行程序，再通过 Python subprocess 组织参数并执行。下载源指向 biliup/biliup。[6]

当前 biliup 的投稿核心与 CLI 位于 Rust crates 中。因此，本项目可以直接从 Rust 调用该原生程序，省掉 SAU 的 Python 包装层；是否进一步链接其 Rust 核心库，需要核查所选版本的公开 API。[7]

B 站适配器只接入本项目需要的登录、凭据检查、投稿和结果查询能力，不引入其完整 WebUI、录播、剪辑或 server 产品流程。不要假定 CLI 已提供稳定的 JSON 进度协议。

### 2.3 “无 Python”的验收口径

- 用户无需安装 Python 或 pip。
- 应用不启动 Python worker，也不内嵌 Python 解释器运行 SAU。
- 主界面不要求启动 Flask、网页开发服务器或浏览器标签页。
- 允许使用浏览器和明确列出的原生辅助程序；无 Python 不等于一个无外部依赖的单文件程序。
- 不预先承诺固定包体、内存占用或上传速度，发布执行成本需实际测量。

## 3. 产品范围与首版默认值

以下平台顺序、页面范围和开发阶段为建议默认值，用户尚未逐项指定。它们用于让工作模式直接开工；在不改变核心方向的情况下可根据实际账号和开发环境调整。

### 3.1 建议的平台顺序

1. 先选一个需要网页自动化的平台完成闭环，默认抖音。它能够尽早验证“Rust 界面 + Rust 浏览器控制”的主路线。
2. 首个平台可靠后接入快手，验证平台适配接口是否能够复用。
3. B 站作为原生程序适配路线接入；若网页平台的登录条件暂不可用，可先验证 B 站的任务接口，但不能据此宣称网页路线已经完成。
4. 小红书、视频号、头条号等后续再扩展。SAU 上游支持某平台，不等于本项目已支持它。

界面只展示实际接入的能力；开发中平台应明确标记，不能把截图里的“15 个平台”直接当作本项目首版承诺。

### 3.2 功能分期

| 功能 | 第一个可用版本 | 后续扩展 |
| --- | --- | --- |
| 账号 | 添加账号、登录、查看状态、重新登录、账号隔离 | 更多平台和账号信息同步 |
| 素材 | 选择本地视频、检查文件、设置封面 | 批量导入、素材检索、更多媒体类型 |
| 内容 | 标题、描述、标签及平台必要字段 | 文案模板、平台专属字段扩充 |
| 发布 | 一个账号完成一次即时发布 | 多账号、多平台批次发布 |
| 任务 | 阶段状态、错误原因、取消、结果待确认 | 更完整的排期、批量重试与诊断 |
| 历史 | 本软件提交的任务与可核实的作品信息 | 从平台同步已有作品 |
| 设置 | 浏览器路径、数据目录、并发、日志 | 自动更新、备份、更多外观设置 |

首阶段不包含粉丝互动、私信、店铺、直播录制、AI 剪辑、全量数据看板。概览只展示本地确实掌握的数据，不虚构粉丝数、播放量或作品总量。

### 3.3 界面建议

- 默认中文界面，统一字体、间距、表单状态和错误提示。
- 主导航建议为“概览、账号、素材、新建发布、任务、设置”，布局可在实现时优化。
- 新建发布页明确展示所选账号、平台、视频和封面，允许为不同平台覆盖内容字段。
- 平台不支持的字段隐藏或给出明确说明，不默默忽略。
- 任务列表显示真实阶段；无法获得准确百分比时显示阶段和等待状态，不模拟进度。
- 主界面中的数据库、CDP、进程参数等实现细节不进入普通用户操作流程。
- 使用 GPUI Kit 的现成控件建立一致界面，先完成核心交互，再细化视觉设计。

## 4. 实现架构与工程组织

### 4.1 职责划分

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| UI | 接收操作、展示状态与结果 | 不直接写平台页面选择器 |
| 应用服务 | 账号、草稿、素材和发布批次 | 不依赖具体窗口控件 |
| 任务引擎 | 排队、同账号互斥、超时、取消、恢复 | 不把所有错误统一重试 |
| 平台适配器 | 各平台的登录、校验、上传、提交、结果确认 | 平台差异集中在这里 |
| 浏览器管理 | profile、CDP 连接、页面和自有进程 | 不使用用户日常浏览器 profile |
| 存储 | 数据迁移、记录和查询 | 不混入页面操作 |
| B 站程序封装 | 版本、参数、输出、取消和结果映射 | 对外服从统一平台接口 |

建议先采用小型 Cargo workspace，避免在首版引入微服务、插件系统或独立守护进程。若工作区已有合理结构，沿用并调整，不为匹配下表而重建工程。

| 建议路径 | 内容 |
| --- | --- |
| Cargo.toml | 工作区与统一依赖 |
| rust-toolchain.toml | 已验证的 Rust 工具链 |
| crates/desktop/ | GPUI Kit 窗口、页面、UI 与后台消息连接 |
| crates/core/ | 数据模型、适配器接口、任务状态机、存储与应用服务 |
| crates/platforms/ | 浏览器管理、抖音/快手适配、B 站程序封装 |
| migrations/ | SQLite 数据库迁移 |
| docs/ | 架构、平台能力、上游参考版本、开发和运行说明 |
| tests/fixtures/ | 本地页面夹具与经过脱敏的示例数据 |

依赖方向：desktop 组合 core 与 platforms；platforms 实现 core 定义的接口；core 不依赖 GPUI 或具体平台模块。

### 4.2 UI 与后台运行

- GPUI 负责窗口事件和绘制；上传、等待、数据库重操作等不阻塞 UI。
- Tokio 后台通过消息/事件向 UI 报告进度、人工操作请求和结果。
- chromiumoxide 的 handler 必须持续被轮询，维持 CDP 事件处理；不能只建立连接后丢弃事件循环。[3]
- 按任务记录本应用启动的浏览器和辅助程序，退出与取消时只清理本应用拥有的进程。
- 首版可在同一 Rust 应用内运行后台任务，等实际出现隔离需求后再拆进程。

### 4.3 平台能力与接口

先定义可扩展的契约，不要求所有平台支持完全相同的字段。

| 接口职责 | 期望结果 |
| --- | --- |
| capabilities | 支持的媒体、字段、封面、定时方式和结果查询能力 |
| login / check_session | 登录状态、账号标识或需要用户完成的操作 |
| validate | 文件及字段校验结果，必须指出具体问题 |
| prepare | 创建上传会话、上传文件、填写内容，停在最终提交之前 |
| submit | 执行一次明确的最终提交，并持久化提交阶段 |
| inspect_result | 根据平台依据返回已提交、明确失败或待确认 |
| cancel | 尽可能停止尚未完成的工作，返回实际停止位置 |

这张表是接口职责设计，不是现成可直接编译的 Rust trait。异步生命周期、类型与错误模型在实现时确定。

“准备”和“提交”之间允许正常任务连续执行，也应支持开发用的 dry-run：走完真实上传准备，但停在最终提交前。

适配器必须声明是否支持准备与提交分离。若外部 CLI 把上传和投稿合为一次命令，在未验证其暂停能力前，不提供“上传后停在提交前”的 dry-run，也不在默认回归中执行该真实投稿命令。调用这类命令前先持久化 Submitting，异常退出且无法确定结果时进入 Unknown。需要完整阶段控制时，再评估其 Rust 核心库接口。

## 5. 任务、数据与账号管理

### 5.1 一个批次拆成独立目标任务

用户选择一个视频、多个平台账号后：

- 创建一个发布批次。
- 每个“平台 + 账号”建立一个子任务，保存当时的内容与配置快照。
- 各子任务独立记录状态和结果。
- 单个平台失败不会把已经成功的目标再次提交。
- 同账号串行执行；首版建议全局并发从 1 开始，验证资源占用和平台行为后再提高。

### 5.2 必须区分的任务状态

| 状态 | 含义与处理 |
| --- | --- |
| Draft / Queued | 草稿或等待执行 |
| Preparing / Uploading | 正在校验、准备或上传 |
| WaitingUser | 等待登录、扫码、验证或其他人工操作 |
| Submitting | 已进入最终提交阶段；执行前先持久化 |
| Submitted | 有可靠依据证明平台已接收；不等于已公开发布 |
| Failed | 已确定失败，附带失败阶段与是否可重试 |
| Unknown | 提交结果不明确，需要查询或人工核对 |
| Cancelled | 尚可停止的工作已停止；不表示平台作品已撤回 |

只有平台提供明确证据时，才能进一步标注“审核中”“已发布”等平台状态。上传进度 100%、点击按钮成功、外部程序退出码为 0，都不足以独立证明内容已经公开发布。

关键行为：

1. 发送最终提交动作之前，先把任务和 attempt 标记为 Submitting。
2. 提交后断网、进程退出或无法识别结果，进入 Unknown；不能直接自动重发。
3. 重启应用时，先恢复记录并判断原任务阶段，不把所有中断任务重新排队发布。
4. 防止重复点击创建相同执行任务；重试使用明确的 attempt 记录。
5. 平台不提供幂等机制时，不承诺绝对只发布一次；用提交前持久化、结果核对和限制重试降低重复风险。
6. 取消发生在最终提交之后，可能只停止本地等待；界面必须保留结果待确认，不能显示“已撤回”。

### 5.3 建议的数据模型

| 模型 | 关键字段 |
| --- | --- |
| Account | 平台、平台账号标识、本地别名、profile 引用、登录状态、检查时间 |
| Asset | 文件路径、大小、修改时间、按需指纹、封面路径 |
| Draft | 通用内容、各平台覆盖字段、素材引用 |
| PublishBatch | 批次 ID、创建时间、所选目标 |
| PublishJob | 平台、账号、内容快照、状态、阶段、排期信息、结果 ID/链接 |
| JobAttempt | 次数、开始/结束时间、错误分类、提交时点、结果依据 |
| JobEvent | 阶段事件、用户可读说明、脱敏诊断信息 |

素材通常引用原文件，不默认复制大视频。执行前重新检查文件存在性及变化；若执行期间文件被删除或修改，给出明确错误。数据库迁移需要版本记录。

### 5.4 登录状态和账号隔离

- 每个账号使用应用管理的独立浏览器 profile，避免账号之间污染登录状态。
- 不直接使用、复制或接管用户日常 Chrome 的默认 profile。
- 同一 profile 加锁，避免多个任务同时读写。
- 应用数据放在操作系统推荐的用户数据目录，不写进安装目录或 Git 仓库。
- 数据库只保存凭据引用和必要元信息；可单独管理的秘密使用系统凭据存储等合适方式。
- 浏览器 profile 自身可能含敏感会话数据，不能因为使用了 SQLite 或系统凭据存储就宣称整个 profile 已加密。
- 日志、错误报告和导出文件不包含 Cookie、token、密码或完整登录资料。
- 登录流程允许显示浏览器窗口；对人工验证给出清楚的继续/取消入口。

### 5.5 定时发布放在基本流程之后

平台原生定时与本地到点执行分别建模：

- 平台原生定时：适配器完成平台时间字段填写，并确认已被接收。
- 本地排期：本软件在指定时间启动发布任务，首版依赖应用后台运行、设备联网且未睡眠。
- 持久化执行时间和时区；展示时使用用户可理解的本地时间。
- 错过排期时标记并让用户处理，不在重启后静默集中补发。
- 对外宣传哪些定时能力，取决于各适配器实际验收结果。

## 6. 开发顺序与交付标准

| 阶段 | 工作 | 验收门槛 |
| --- | --- | --- |
| M0：环境与骨架 | 检查目标 OS、Rust、GPUI Kit；窗口、中文输入、文件选择；启动浏览器并连接 CDP | 真实桌面窗口可运行；无 WebView 主界面；UI 不依赖 Python；浏览器事件和退出正常 |
| M1：核心与存储 | 数据模型、SQLite 迁移、账号/素材页面、队列、状态事件与模拟适配器 | 重启数据保留；同账号互斥；模拟任务明确标记；UI 能响应后台状态 |
| M2：首个平台闭环 | 登录、恢复会话、真实文件上传、填写内容、dry-run、结果确认 | 真实页面流程可验证；缺文件、登录失效、页面变化有明确反馈；经过真实发布验收才标记支持 |
| M3：可靠性 | 取消、断线、超时、重复点击、应用退出与重启 | 提交后未知结果不自动重发；不会误报撤回或发布成功；无自有孤儿进程 |
| M4：扩展与交付 | 第二个平台、B 站可选适配、批次和排期、安装包 | 新适配器复用核心；平台差异可见；目标系统干净环境可安装运行 |

第一轮开发应优先完成 M0、M1，并进入 M2。不要先花大量时间画完所有平台页面，也不要用模拟成功代替真实上传集成。

### 6.1 有意义的验证

- 编译、格式检查与必要的静态检查。
- 对状态转换、重复提交防护和恢复逻辑做测试。
- 用本地页面夹具验证文件上传、弹窗和等待逻辑；这不能替代目标平台实测。
- 默认自动化回归仅执行可分离的发布准备并停在最终提交前；无法分离的 CLI 路线使用模拟或本地夹具。真实发布验收使用用户指定的账号和素材，由明确的发布操作或已授权任务触发。
- 在真实目标设备验证中文输入、缩放、文件选择、账号登录和退出清理。
- 打包后验证应用不需要用户安装 Python，不能只在开发机上运行通过。

### 6.2 每个阶段的交付说明

工作模式每次汇报应给出：

- 已实现并运行的行为。
- 实际执行过的构建或验证及结果。
